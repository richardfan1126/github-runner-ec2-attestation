# container-security — Design Rationale

> Imported from spec-kit `specs/001-container-security-config/` (research.md, plan.md, data-model.md) and `specs/002-scratch-tmpfs-exec/` (research.md). Captures the *why* behind `spec.md`; not normative.

## Overview

The nine container-security settings parameterize the execution-container sandbox so its posture can be tuned per-deployment without code changes, while every setting defaults to the secure choice and every effective value is observable for attestation. The feature is a *parameterization of existing literals* in `script_executor.py`, not new machinery — the executor already set `security_opt`, `cap_drop`/`cap_add`, and a read-only `/workspace` bind; these decisions just make those values configurable, validated, and attested.

## Key decisions & trade-offs

- **Capability allow-list = the 14-cap Docker default-bounding set; default-granted = today's 7.** Unset grants the existing 7-cap working set (preserving current behavior); the allow-list is the broader, well-vetted Docker default-bounding set. So operators can grant *more* than today without forking, but cannot request dangerous caps (`SYS_ADMIN`, `SYS_PTRACE`, `NET_ADMIN`, …) without a code change. *Rejected:* exactly-7 (too rigid) and any-Linux-cap (weakest guardrail). Names match the Docker SDK form: upper-case, no `CAP_` prefix, case-sensitive.
- **`CONTAINER_USER` requires full `uid:gid`.** A bare uid is rejected even though Docker permits it, because the **attested** value must be unambiguous and not depend on image/runtime gid defaults — attestation determinism over convenience.
- **Unset ≠ empty (caps and tmpfs).** `CONTAINER_CAP_ADD` unset = default 7; empty = none on top of `drop ALL`. `CONTAINER_TMPFS_SIZE` unset/empty = no tmpfs mounted (an explicit, valid choice that must not be silently overridden). This distinction is testable and surfaced in the attested value.
- **tmpfs scratch mounts at `/tmp`, governed solely by size.** Mounting at the conventional `/tmp` (not a sub-path) is what makes a hardened-default, read-only-rootfs job actually work, because standard tooling (`$TMPDIR`, `mktemp`, `tempfile`) writes there. The mount is independent of `CONTAINER_READ_ONLY_ROOTFS`, so the attested `container_tmpfs_size` is always the effective value. (An earlier draft targeted `/tmp/execution`, referenced only by dead code — the live flow runs `bash /workspace/{script_path}` from the read-only workspace.)
- **tmpfs exec is one extra option on the *same* mount.** `CONTAINER_TMPFS_EXEC` conditionally appends `,exec` to the existing `{"/tmp": "size=…,mode=1777"}` string. Docker brings `--tmpfs` up `rw,nosuid,nodev,noexec` unless `exec` is requested, so this guarantees `nosuid`/`nodev`/`mode=1777`/size are untouched — only execution permission changes. The disabled path is kept byte-identical to today's string so existing deployments and executor tests are unaffected. Enabled-but-no-tmpfs resolves and attests the value, applies no mount change, and emits a startup **warning** (not a fail-fast) — the setting is orthogonal to whether a mount exists, and failing would punish a benign config.
- **Reuse the existing validation, flow-through, and attestation seams.** Parsing/validation live in `ServerConfig.from_env()`/`validate()`, raising `ValueError`→`ConfigurationError` so the process exits before binding the port (identical to every existing option; booleans reuse `parse_strict_bool`). Effective values map directly onto `docker.containers.create()` kwargs (`user`, `cap_drop`/`cap_add`, `security_opt`, `read_only`, `tmpfs`, workspace bind `mode`, `network_mode`). Effective values are threaded into attestation `user_data` exactly as `gpu_enabled` already is. `CONTAINER_ALLOW_ROOT` is a startup root-gate only — it is **not** threaded into container creation (it doesn't shape `containers.create()`), but it is still attested. *Rejected:* a separate validation module, a dedicated posture endpoint — both redundant with the existing single-`ServerConfig` + `user_data` channel.
- **Hardened defaults are an accepted breaking change.** Non-root user, read-only rootfs, read-only workspace, and `none` network will break jobs that relied on the old insecure Docker defaults; each breaking default is documented with its symptom and named opt-out. Making the safe configuration the default — what an operator gets by doing nothing — is the core value of the feature.

## Build-time configuration summary (drift-proof)

`.github/scripts/print_config.py` resolves the image's baked-in env file through the executor's own `load_config()` and renders **every** `dataclasses.fields(ServerConfig)` entry — so the printed values are exactly what the server would resolve (single source of truth) and **cannot drift** from the code. Settings are grouped into ordered per-category subsections via a maintained `CONFIG_CATEGORIES` map, with a catch-all **"Other"** group (rendered last) automatically collecting any unmapped field — so a newly added field is never silently dropped, without a build-breaking assertion. The helper lives in `.github/scripts/` (build tooling), **not** `src/` (executor runtime), but imports `src.config` so the executor stays authoritative; it imports only `src.config` so it never binds a port or touches the TPM. The summary step runs in `build-and-publish` before the GHCR push, failing the run if the loader rejects the baked-in env — the same failure the server would hit at startup, caught early. *Rejected:* echoing/parsing the env file (misses the defaulted settings, drifts from real parsing), a hand-maintained list (drift), and booting the full server with `--print-config` (needs TPM/port + heavyweight imports).

## Data models (shapes)

A **container security configuration** of nine settings, each with a secure default, an accepted form, and an effective resolved value used for container creation and surfaced for attestation; a closed **capability allow-list** (14 caps) with the 7-cap default working subset; the **execution container** whose posture the resolved config determines; and the **attestation/audit surface** tying an execution to the effective values it ran under (`container_user`, `container_allow_root`, the resolved cap list, `no_new_privileges`, `container_read_only_rootfs`, `container_tmpfs_size`, `container_tmpfs_exec`, `workspace_mount_mode`, `container_network_mode`).
