## Why

The `build-ami` stage fans out as a per-flavor matrix, and each matrix leg independently runs `scripts/build-ami.py`, which provisions its **own** EC2 build instance (plus VPC, IAM role/policy/instance-profile, and security group) via Terraform. Because those AWS resources use globally-fixed names (`build-ami-instance-role`, `build-ami-instance-policy`, `build-ami-instance-profile`, `build-ami-instance-sg`), two legs running concurrently (`max-parallel: 2`) collide with `EntityAlreadyExists` / duplicate-name errors. Every leg also re-provisions a full `c5.9xlarge` and **re-compiles `coldsnap` from source** (plus Rust, ORAS, gh CLI) — flavor-independent work repeated once per flavor.

## What Changes

- **BREAKING (pipeline internals):** Replace the per-flavor `build-ami` matrix with a **single** `build-ami` job that provisions **one** shared build instance, installs the toolchain **once**, then loops over all selected flavors to build each AMI on that instance.
- Move Terraform lifecycle ownership out of `scripts/build-ami.py` and into the workflow: a `terraform apply` step provisions the instance once, and an `always()` `terraform destroy` step tears it down once. The script no longer runs `terraform apply`/`destroy` in its own `finally` block.
- **Keep `terraform apply` and `terraform destroy` in the same job / on the same runner.** The build-ami Terraform state is gitignored and local (no remote backend), so destroy can only tear down what apply wrote to that runner's filesystem. This is a hard constraint of the ownership move: provisioning **cannot** be split into a separate job from teardown without first introducing a remote/persisted backend. The current single-job layout satisfies this; it is recorded so a later refactor does not silently break teardown.
- **Add a runner-death backstop: make the build instance self-terminating.** `always()` destroy covers step failure and normal cancellation but structurally cannot fire on runner hard-death, the ~6 h ceiling force-kill, an exceeded cancellation grace period, or the destroy step itself erroring — and the instance today has no `user_data`, no `instance_initiated_shutdown_behavior`, and only a fixed `Name = "build-ami-instance"` tag, so an orphan is invisible and bills indefinitely. Add an unconditional self-destruct that does not depend on the runner: `user_data` running `shutdown -h +<TTL>` (a TTL comfortably longer than a normal run) plus `instance_initiated_shutdown_behavior = "terminate"`, and a **run-id tag** so any orphan is identifiable (and optionally sweepable out-of-band). This is the transient **builder** instance, not the runtime AMI, so adding `user_data` here has **no attestation/PCR impact**. The run-id tag is the same idea as the run-scoped resource naming already proposed — collision-avoidance and orphan-observability from one identifier. With this in place the only remaining orphan window is "runner dies **and** the TTL has not yet elapsed," which self-heals at the TTL. The TTL is coupled to an explicit job `timeout-minutes` (which the build-ami job lacks today, so it inherits GitHub's 6 h default): this change **adds** `timeout-minutes: 120` and sizes the TTL just above it (`shutdown -h +150`), holding the invariant `worst-case run << timeout-minutes < TTL` so the TTL only ever fires on true runner hard-death (see design D2).
- **Make the single `always()` teardown retry and fail loud.** `terraform destroy` can exit non-zero from transient causes (API throttling, dependency/in-use races, eventual consistency), leaving resources alive even though the step ran. Because this change removes the script's `finally` destroy, teardown collapses from today's **two** attempts (script `finally` + workflow `always()`) to a **single** `always()` attempt, which therefore must be robust: retry destroy with backoff (safe because destroy is idempotent/convergent — a re-run only removes what remains) and, if it still cannot converge, surface the failure visibly rather than green-washing a possible orphan.
- Refactor `scripts/build-ami.py` so its unit of work is "build one AMI on an already-provisioned instance": it accepts the instance connection details (host + SSH key) instead of provisioning infrastructure. A thin driver iterates the selected flavors, installing tools once and reusing the SSH session.
- Preserve per-flavor **failure isolation**: a single flavor's build failure is recorded and skipped, the loop continues, and successful flavors still emit their `ami_build_result-<flavor>.json`, matching today's matrix behavior that `update-flavors-lock` already tolerates. Collapsing N per-flavor instances into one shared instance converts N independent failure domains into a single shared one, so this guarantee is **not free** — it requires the two robustness changes below, without which a single host/SSH fault silently takes down the whole run.
- **Bound the SSH command wall-clock and detect transport death.** `execute_remote_command` currently loops on `while not stdout.channel.exit_status_ready(): … time.sleep(0.1)` with **no timeout and no channel-liveness check**; paramiko does not raise when the instance dies mid-command, so the channel simply never reports ready and the loop spins forever. Under the matrix this only ever wedges one leg (killed by the GitHub job timeout); on a shared instance a hang during flavor 1's `coldsnap upload` means flavors 2 and 3 **never start** and the per-flavor `try/except` never runs. This change adds a wall-clock timeout plus transport-liveness detection so a dead host becomes a **raised exception** instead of an infinite spin — the precondition that makes per-flavor isolation real on a shared host.
- **Split the failure taxonomy so the loop reacts to the *kind* of failure.** An **application error** (non-zero exit, signature/validation failure, `RuntimeError`) means the host is healthy → record that flavor as failed and **continue** to the next. An **SSH/transport error or command timeout** means the host is suspect → **stop attempting further Pass 1 flavors** (each would only time out), record them as skipped, but **still run Pass 2** for snapshot IDs already captured and **still run the `always()` destroy**. The two are cleanly distinguishable: a raised paramiko/timeout exception ⇒ host-suspect (abort remaining Pass 1); a non-zero exit or validation `RuntimeError` ⇒ flavor-local (continue).
- **Rely on the two-pass split as the isolation backstop.** `wait_for_snapshot` and `register_ami` run against the boto3 `ec2_client` on the GitHub runner, **not** over SSH, so once a flavor's `coldsnap upload` returns a snapshot ID it can be waited on and registered **even if the build instance dies**. `coldsnap upload` returning is therefore the last host-dependent moment, and the host-fault blast radius shrinks with each completed upload: already-uploaded flavors are immune, only the in-flight and not-yet-started flavors are lost. The ultimate backstop remains `update-flavors-lock`'s carry-forward of any missing per-flavor result, and there is no attestation/trust impact from a skipped flavor.
- Reset the shared artifacts working directory (`~/artifacts`) at the start of **each** flavor iteration (**wipe-and-reuse**) so every flavor builds from a known-empty tree. On a shared instance this is required for both **correctness** — the register/upload path enforces exactly one `.raw` in `build-output`, which a previous flavor's leftover would violate — and **capacity** — only one flavor's OCI blob + unpacked `.raw` ever occupies the 30 GB root at a time, instead of all flavors accumulating. The artifacts base path is passed to the build routine as a single named parameter (defaulted to `~/artifacts`) rather than re-hardcoded, so a future move to parallel per-flavor subdirectories is a small change rather than a re-thread of every call site.
- Execute the flavors as a **two-pass (hybrid) model** rather than fully serializing each flavor end-to-end. **Pass 1** iterates the flavors sequentially — for each: wipe, pull, verify, validate, and `coldsnap upload` — capturing the returned snapshot ID and then discarding the `.raw` (the snapshot lives server-side once upload returns, so the disk can be wiped for the next flavor). **Pass 2** then waits for all captured snapshots to reach `completed` and registers each AMI. This keeps uploads **sequential** (preserving wipe-and-reuse and avoiding EBS `PutSnapshotBlock` contention) while **overlapping the passive per-snapshot completion wait** — a poll-based waiter that can block up to ~10 minutes per flavor — which naive full serialization would otherwise pay back-to-back. Per-flavor failure isolation still applies within each pass: a flavor that fails Pass 1 is recorded and excluded from Pass 2; a flavor that fails its Pass 2 wait/register is recorded without aborting the others.
- Add run-scoped uniqueness to the Terraform build-instance resource names (defense-in-depth so any future concurrency — e.g. overlapping runs across refs — cannot collide on account-global IAM names).
- **Right-size the build instance from `c5.9xlarge` to `c5.4xlarge`.** The 36-vCPU type existed to make the CPU-bound `coldsnap` compile fast *per leg*; compiling **once** (not per flavor) removes that justification. Every remaining phase is instance-insensitive — `coldsnap upload` uses a hardcoded 64 `PutSnapshotBlock` workers and is bounded by the EBS Direct API throttle, not cores/NIC, so uploads do not slow on a smaller instance; snapshot waits are idle. `c5.4xlarge` keeps the (now once-per-run) compile gate fast and its ~5 Gbps baseline clears any single 64-worker upload, at roughly half the cost. See design D11 (with an empirical-confirmation caveat; `c5.2xlarge` is a fallback).

### Modified Capabilities

## Impact

- **Workflow:** `.github/workflows/build-attestable-image.yml` — the `build-ami` job is restructured (matrix removed; adds provision, per-flavor build loop, and always-destroy steps); the hardcoded `-var "instance_type=c5.9xlarge"` on the Terraform apply becomes `c5.4xlarge` (design D11); the job gains an explicit `timeout-minutes: 120` (it has none today, so it inherits GitHub's 6 h default), paired with the self-destruct TTL (design D2). `update-flavors-lock` is unaffected (still consumes `ami-build-result-*` artifacts).
- **Script:** `scripts/build-ami.py` — provisioning/cleanup of infrastructure is decoupled from the per-AMI build; new arguments for instance host / SSH key; a multi-flavor driver with per-flavor error handling structured as two passes (Pass 1: sequential wipe→pull→verify→validate→upload capturing snapshot IDs; Pass 2: batched snapshot-completion waits + AMI registration); `execute_remote_command` gains transport-liveness/progress detection (primary) plus a generous wall-clock backstop so a dead host raises instead of spinning forever without false-aborting legitimately long uploads/compiles; the driver distinguishes application errors (continue) from SSH/transport errors and timeouts, attempting a bounded SSH reconnect-and-resume (at the flavor boundary) before falling back to abort-remaining-Pass-1 (still run Pass 2 + cleanup); the artifacts working directory is reset before each flavor's pull (wipe-and-reuse) and its base path is a single parameter rather than a hardcoded constant.
- **Terraform:** `terraform/build-ami/` — a new `run_id` var (`${github.run_id}-${github.run_attempt}`, passed identically on apply and destroy) run-scopes the account-unique names (IAM role/policy/profile, SG `GroupName`, ssh `key_name` — replacing the existing non-deterministic `timestamp()` suffix) and tags all resources; other resources (VPC/subnet/instance) are only tagged, not renamed; the instance gains `user_data` (`shutdown -h +<TTL>`), `instance_initiated_shutdown_behavior = "terminate"`, and the run-id tag as a runner-death orphan backstop; no change to the security posture (isolated VPC, IMDSv2, region/account-scoped IAM).
- **No change** to the runtime NitroTPM attestation, `user_data`, PCR semantics, the published artifact annotations, or the `flavors.lock` record format — this is a build-pipeline efficiency/correctness change only.

## Notes

### Out of scope — observed adjacent bug: GPU image-size bump is a silent no-op

While confirming the per-flavor `.raw` disk footprint for the wipe-and-reuse decision above, we found that the GPU image-size increase does not currently apply. `.github/scripts/build-kiwi-image.sh` bumps the image only via `sed -i 's/<size unit="G">4<\/size>/<size unit="G">8<\/size>/'`, but `kiwi-descriptions/appliance.kiwi` now carries `<size unit="G">5</size>` — the base was raised `4 → 5` in `9908bb7` (rust-build disk increase) without updating the GPU `sed`, which was written against `4` in `bd9da29`. Because the pattern no longer matches, GPU builds get a **5 GB** image instead of the intended **8 GB**, squeezing the NVIDIA driver + Container Toolkit (~1.5 GB) into the same size as the other flavors; the accompanying comment ("The base image is 4GB") is also stale.

This is an **`image-build`** defect, independent of this change, and is **not** fixed here — it is recorded only so it is not lost. It does **not** affect the sizing conclusion for `single-instance-ami-build`: even at the intended 8 GB, a single flavor's `.raw` fits comfortably on the 30 GB root under wipe-and-reuse. Recommended follow-up: a separate small change that makes the size bump robust to the base value (e.g. template the size or match on the current value) rather than string-matching a stale literal.
