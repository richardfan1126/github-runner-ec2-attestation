## Why

Today the attestation records only `gpu_enabled: true` — a single server-config boolean that says a GPU was passed through, but nothing about *which* GPU or *which* driver/CUDA stack computed the result. For attested GPU workloads (e.g. model quantization in CI), a verifier wants the measured GPU identity itself: device name, UUID, driver version, CUDA/VBIOS versions, per-device details — sourced from the PCR4-measured NVIDIA driver via NVML, so the self-report is trustworthy — and eventually a reference to a hardware NVIDIA GPU-attestation (NRAS) report. **That is the feature: enrich the attestation with GPU information.**

The blocker is structural. The NitroTPM `user_data` field is hard-capped at **1024 bytes** (`src/attestation.py` rejects overflow), and the current inline layout — `repository_url`, `commit_hash`, `script_path`, `script_env_hash`, `timestamp`, `execution_id`, `gpu_enabled`, plus the nine-field container-security posture — already sits close to that ceiling; the code comment itself notes a long repository URL plus an expanded `CONTAINER_CAP_ADD` can cross it. GPU identity (a per-device array of UUIDs and versions) does not fit inline, and every future field makes it worse. The system already solves this exact problem twice — `server_public_key` stores a SHA-256 fingerprint with the full key delivered alongside, and `script_env_hash` stores a digest of an external preimage — so we generalize that established idiom to the whole `user_data`, then add the GPU information on top of the headroom it creates. The two goals are co-equal: the claims-digest envelope is the enabler; the GPU enrichment is the payload the user actually wants.

## What Changes

- **BREAKING (wire format):** Replace the inline `user_data` field set with a compact signed envelope `{ v, claims_digest, timestamp, execution_id }`. The TPM signature covers the whole envelope, so `execution_id` stays inline for cheap, signed correlation that needs no preimage fetch; `claims_digest` binds a full **claims document** carried alongside the attestation in the response body, unconstrained by the 1024-byte limit. Envelope fields are authoritative and are **not** duplicated inside the claims document, so verifiers never reconcile two copies.
- Introduce a versioned **claims document** schema (`schema_version`, digest-algorithm agility via a `sha256:` prefix) carrying today's fields (`repository_url`, `commit_hash`, `script_path`, `script_env_hash`, `execution_id`, the `security` posture block).
- **Add GPU information to the attestation:** a new **`gpu` claims block** replacing the bare `gpu_enabled` boolean with `{ enabled, devices: [ { uuid, name, driver_version, cuda_version, vbios_version, compute_capability, memory_total_mib } ] }`, collected at attestation time from the PCR4-measured NVIDIA driver via NVML (so the report is only as trustworthy as the measured driver — and it is measured). `gpu_enabled` is retained inside the block as `enabled` for continuity. When `ENABLE_GPU` is false the block is `{ enabled: false }`.
- Bind the claims by **hashing the transmitted bytes** of the claims document (not a re-canonicalized form), so independent verifiers need no cross-language JSON canonicalization to check the binding. Canonicalization rules are retained only for *inner* sub-digests whose preimage lives elsewhere (`script_env_hash`).
- Reserve a **nested digest-and-preimage** slot for a future NVIDIA GPU-attestation (NRAS) report (`gpu.attestation.report_digest`), applying the same indirection recursively rather than inlining a large report.
- **Unify** the two attestation builders (execute-time and output-time) under the single envelope shape; they differ only in their claims body (`execution` claims vs `output` claims, the latter still carrying the `stdout‖stderr‖exit_code` digest).
- Update the verifier contract and README: consumers must now hash `claims_raw`, compare against `claims_digest`, reject unknown `schema_version`, *then* read fields — the attestation is no longer self-describing and must travel bundled with its preimage.

This is a **software/schema-level change only**: `user_data` is not part of measured boot, so PCR4/PCR7, the sealed image, and the flavor/AMI pipeline are unaffected. No AMI rebuild is required.

## Capabilities

### New Capabilities
- `attestation-claims`: The claims-document envelope format — the compact signed `user_data` (`{ v, claims_digest, timestamp, execution_id }`), the versioned claims schema and its canonicalization/digest rules, the hash-the-transmitted-bytes binding, the envelope/claims field partition (inline envelope fields are not repeated in the claims document), and the verifier binding-check contract (recompute digest → reject unknown version → read). Capability-agnostic about *which* claims are carried.
- `gpu-attestation`: The GPU information carried in the attestation — the `gpu` claims block and its fields, that they are collected from the PCR4-measured NVIDIA driver via NVML (and the resulting trust semantics: measured-driver self-report, not hardware attestation), per-device array handling for multi-GPU instances, the `{ enabled: false }` shape when GPU is disabled, the reserved nested slot (`gpu.attestation.report_digest`) for a future NVIDIA NRAS hardware-attestation report, and the supported-instance bound (NitroTPM attestation exists only on specific *virtualized* accelerated instances — G4dn/G5/G6/G6e/Gr6/G7 and P5/P5e/P5en/P6 — **not** P4d/P4de (A100), P3 (V100), or bare-metal, so the claim is unattainable on unsupported accelerators).

### Modified Capabilities
- `remote-executor`: The "Attestation document generation and execution initiation" requirement changes — `user_data` no longer carries the documented inline fields directly; instead it carries `claims_digest` binding a claims document, and `/execute` and `/execution/{id}/output` responses must include the corresponding `claims_raw` preimage inside the existing sealed response body. The `execution_id`-binds-the-attestation and `script_env_hash` scenarios are restated in terms of the claims document.

## Impact

- **Code:** `src/attestation.py` (both `generate_attestation` builders → unified envelope + claims assembly, new GPU/NVML collection), `src/server.py` (response assembly to include `claims_raw` on `/attest`, `/execute`, `/execution/{id}/output`), `src/main.py`/`src/config.py` (GPU claim sourcing when `ENABLE_GPU`).
- **Wire format / consumers:** BREAKING for any attestation verifier — the `github-runner-ec2-attestation-rust-build-demo` caller and any downstream consumer must adopt the recompute-and-compare flow and read fields from `claims_raw`. Requires a versioned rollout keyed on `schema_version`.
- **Docs:** README Encryption/attestation sections and API endpoint response schemas; the verifier flow gains a mandatory digest-binding check (mirroring the existing `server_public_key` fingerprint check).
- **Not impacted:** PCR4/PCR7 measurements, the KIWI sealed image, `flavors.lock`, and the AMI-build/deploy pipeline — `user_data` is unmeasured, so no rebuild. The `request-encryption` capability is also unaffected: `claims_raw` rides inside the existing sealed response body and inherits confidentiality from the current "seal the body" requirement — no encryption-spec change.
